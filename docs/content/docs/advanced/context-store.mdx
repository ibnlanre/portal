title: Scoped Stores (Context)
description: Create scoped store instances from component context and props.

Use a context store when a state tree belongs to a component boundary rather
than the whole application. It is especially useful when you need:

1. It is initialized with data from `props`.
2. It exists only for a specific part of your app (like a single tab in a dashboard).
3. It has multiple instances active at once.

`createContextStore()` gives you the best of both worlds: the power of Portal's API with the scoping of React Context.

## The Problem

If you use a global `createStore()`, you can't easily initialize it with data from your component's props, because the store is created _before_ the component mounts.

```tsx
// ❌ Hard to pass 'initialCount' dynamically
const globalStore = createStore(0);
```

## The Solution

`createContextStore` lets you define a "store creator" function. This function runs inside a Provider component, meaning it has access to props and hooks.

Because a provider re-runs its factory on every render, initialize the store
once with `useState` so the same instance survives rerenders:

```tsx
import { createContextStore, createStore } from "@ibnlanre/portal";
import { useState } from "react";

// 1. Create the Context Store factory.
// The factory receives the props passed to the Provider.
const [CounterProvider, useCounterStore] = createContextStore(
  (props: { start: number }) => {
    // Initialize once; later provider renders reuse this store.
    const [store] = useState(() => createStore(props.start));
    return store;
  }
);
```

A factory that returns a fresh `createStore(...)` on every render resets state
whenever the provider rerenders, so keep the lazy initializer as the default
shape.

Now you can use it in your app:

```tsx
function App() {
  return (
    <>
      {/* Two independent stores! */}
      <CounterProvider value={{ start: 10 }}>
        <CounterDisplay id="A" />
      </CounterProvider>

      <CounterProvider value={{ start: 100 }}>
        <CounterDisplay id="B" />
      </CounterProvider>
    </>
  );
}
```

## Consuming the Store

Inside your components, `useCounterStore()` returns the specific store instance for that tree. You can then use the standard `$use()`, `$get()`, and `$set()` methods.

```tsx
function CounterDisplay({ id }: { id: string }) {
  // Get the store instance for this context
  const store = useCounterStore();

  // Use it just like a global store
  const [count, setCount] = store.$use();

  return (
    <button onClick={() => setCount(count + 1)}>
      Counter {id}: {count}
    </button>
  );
}
```

## Recreating on purpose: memoized factories

Sometimes a new store _is_ the intent — for example when a `props.id` change should
start a fresh instance. Key the factory to those props with `useMemo` or Portal's
`useSync` so the store is replaced only when that key changes:

```tsx
import { createContextStore, createStore, useSync } from "@ibnlanre/portal";

const [UserProvider, useUserStore] = createContextStore(
  (props: { id: string; name: string }) => {
    // Recreate the store only when props.id changes; render-to-render
    // rerenders with the same id keep the same instance.
    return useSync(() => {
      return createStore({ id: props.id, name: props.name });
    }, [props.id]);
  }
);
```

Creators remain fully general — they can call any hook and build a store from
anything, including values a schema cannot describe. Portal's context
integration requires React 19.
