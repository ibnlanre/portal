title: Reading State

---

Use `$get()` to read state imperatively — inside event handlers, utilities, or actions.

```ts
import { z } from "zod";
import { createStore } from "@ibnlanre/portal";

const countStore = createStore(z.number(), 10);
countStore.$get(); // 10
```

## Selectors and Fallbacks

`$get()` accepts a **selector** function to derive a value, or a **fallback** value when the store value is `undefined`:

```ts
const userStore = createStore(
  z.object({ firstName: z.string(), lastName: z.string() }),
  { firstName: "Alex", lastName: "Johnson" }
);

// Derive a value with a selector
userStore.$get((u) => `${u.firstName} ${u.lastName}`);
// "Alex Johnson"
```

```ts
const configStore = createStore(
  z.object({ apiUrl: z.string().optional() }),
  { apiUrl: undefined }
);

// Fallback when the value is undefined
configStore.apiUrl.$get(); // undefined
configStore.apiUrl.$get("https://api.default.com"); // "https://api.default.com"
```

Selectors are pure functions — the store never caches derived results,
so use them for cheap computations.

## Reading from composite stores

Each nested node is itself a store with `$get`:

```ts
const store = createStore(
  z.object({ settings: z.object({ theme: z.string() }) }),
  { settings: { theme: "dark" } }
);

store.settings.$get(); // { theme: "dark" }
store.settings.theme.$get(); // "dark"
```

## Dynamic paths with `$at()`

When the property name isn't known at write time:

```ts
const key = "settings.theme";
store.$at(key).$get(); // "dark"
```

## Cheap vs expensive selectors

Selectors run synchronously inside `$get`. For expensive computations or
React re-render gating, prefer `$use()` with a selector instead — it only
re-runs when the source path changes.
